---
title: fireEngine 0.10 architecture
---

Release 0.10 renders a directional shadow map, then samples it while drawing
the camera view. The interactive application loads and animates the textured
AnimatedCube and adds a procedural ground plane that receives shadows without
casting them. The renderer has two explicit graphics passes, two reusable frame
slots, and an optional helper for recording the forward pass.

This document describes the complete system at [tag 0.10][source-tree]. It
stands on its own; earlier architecture pages are not prerequisites. It records
the released design and its limits. The investigations and rejected changes
belong in the accompanying posts.

The pinned source tree is the implementation reference, and the
[release notes][release] summarise the delivered behaviour. Generated
[public documentation][public-docs] and [internal documentation][internal-docs]
track the current tutorial revision and can diverge from this tag. The
[Terminology page][terminology] explains the project vocabulary used here.

## The organising decision

Each pass receives the data and recording context it needs; resource ownership,
frame retirement, submission and presentation remain with the renderer's
coordinating thread.

One frame compiler resolves the immutable scene draw list into two restricted
inputs. The shadow recorder receives caster geometry and transforms. The
forward recorder receives every draw, its material state, and the selected
frame slot's shadow map. Neither input exposes a mutable scene, allocator,
queue or RAII resource owner.

```text
application scene + camera + light view
                  |
                  v
         immutable frame input
                  |
       +----------+-----------+
       v                      v
shadow input             forward input
caster geometry          all geometry + materials
       |                      |
       v                      v
shadow primary           forward primary + secondaries
       |                      |
       +----------+-----------+
                  v
       one ordered queue submission
          shadow, then forward
```

The diagram shows the two consumers of the frame input, not parallel pass
recording. The CPU records the shadow pass first, then the forward pass. Only
forward secondary recording may involve a helper. A barrier makes the shadow
depth writes visible to forward sampling; command-buffer order alone is not
the memory dependency.

The design uses concrete `ShadowRecorder` and `ForwardRecorder` types. There
is no pass base class, render graph, general scheduler or additional submission
queue. The [renderer implementation][source-renderer] makes the fixed sequence
explicit.

## System map

Application content remains independent of Vulkan. The application owns the
world and view choices; the renderer owns their device representation.

| Area | Responsibility | Dependencies within the engine |
| --- | --- | --- |
| `math/` | Vectors, quaternions, transforms and matrices | none |
| `graphics/` | Assets, typed IDs, preparation requirements and CPU capture encoding | maths; scene draw views in preparation implementation |
| `scene/` | Forest ownership, stable scene-local IDs and draw-list construction | maths, graphics IDs, animator bindings |
| `animation/` | Rotation channels, validation and playback | maths and scene |
| `content/` | Composition of assets, scene and animations | graphics, scene, animation |
| `gltf/` | Supported glTF data translated into engine content | content; graphics and scene types internally |
| `render/` | Vulkan-free frame/view descriptions, renderer façade, outcomes and timings | maths, graphics, scene and platform values |
| `render/detail/` | GPU resources, input compilation, concrete passes and frame protocol | Vulkan, VMA and compiled Slang shaders |
| `platform/` | GLFW lifetime, window, events, framebuffer dimensions and surface | GLFW and Vulkan at surface creation |
| `app/` | Loading, receiver fixtures, event loop, scenarios and benchmarks | the public engine interfaces |

`core/` supplies logging and internal helpers and is omitted from the other
rows. The scene/preparation implementation relationship is a source-level
dependency, so this table is not a claim that every directory forms an acyclic
layer stack. `Window::createVulkanSurface()` deliberately keeps the platform
surface boundary Vulkan-aware.

The [public renderer][source-api] is non-copyable and non-movable and owns one
implementation pointer. Calls on one renderer must be serialized by the
application. Internal recording concurrency does not make the public API safe
for concurrent calls.

## Application state and stable preparation

`SceneContent` owns three kinds of CPU state: `RenderAssets`, the `Scene`, and
reusable animation channels. Assets connect meshes, materials, textures and
decoded images through distinct typed IDs. A `RenderObject` relates geometry
to a material and carries the default-true `castsShadow` property.

The scene owns a forest through unique pointers and maintains a dense,
non-owning lookup of node pointers. Nodes receive scene-local IDs when inserted;
world-transform updates do not assign identities. The component variant gives
a node one role, so imported mesh primitives use children beneath their source
transform when necessary. Node removal, reparenting and ID reuse are absent.

Animation playback changes local rotations and animator state. Rotation
interpolation uses shortest-arc SLERP with a near-equal numerical fallback;
looping and clamping operate on the clip time. World transforms are then
resolved, and `Scene::buildDrawItems()` writes ordered render-object IDs and
world matrices into a reusable `SceneDrawListArena`. Its returned span expires
when the arena is reused or destroyed. See the [scene][source-scene] and
[playback][source-animation] implementations.

Stable assets are prepared separately from that per-frame work:

```text
RenderAssets + SceneDrawList + PipelineDescription
                         |
                         v
                 RenderPreparation
                  validated plan
                         |
                         v
                 ResourceCompiler
                  candidate graph
                         |
                         v
                CompiledResources
```

`Renderer::prepare()` drives this sequence. [Preparation][source-preparation]
validates the assets, selects the resources required by the ordered draws and
caches the result. The key includes collection identity and revision, the
pipeline requirement, and the exact ordered render-object sequence alongside
its hash. Transforms are absent, so animation alone does not invalidate
prepared resources.

Both pipelines use the same interleaved vertex layout. The shadow pipeline
consumes its position attribute; it does not require a separately compiled
mesh or another preparation walk. Cast participation passes through the plan
and compiled object so the frame compiler can filter the shadow sequence.

An unchanged prepared generation returns without waiting or allocating. A
changed generation retires earlier work, compiles a complete candidate and
installs it only after compilation succeeds. The [resource compiler][source-resources]
owns its own upload pool and fence. Image uploads are synchronous and do not
borrow a frame slot's recording state.

The [compiled graph][source-graph] owns images, textures and meshes; resolved
object packets contain plain handles. Ordinary asset owners use unique
pointers. The white fallback image and its texture use shared pointers so a
replacement graph can retain them without another image upload. That limited
sharing is distinct from incremental reuse of arbitrary changed assets.

## One lookup, two restricted inputs

The application supplies a [FrameDescription][source-description] containing
its perspective camera and orthographic `DirectionalShadowView`. The renderer
derives the camera matrix using the current presentation extent and the light
matrix using the supplied shadow bounds. It retains no mutable camera or
light-placement policy.

The [frame-input compiler][source-input] resolves each draw through a
`CompiledResourcesView` once. It appends a forward packet unconditionally and
a shadow packet only when that object casts shadows. Both sequences preserve
the source order; the receive-only plane stays in the forward sequence.

```text
FrameRecordingInput
├── FrameUniforms
│   ├── camera view-projection
│   └── light view-projection
├── ShadowRecordingInput
│   ├── fixed pipeline and uniform handles
│   └── caster geometry + model transforms
└── ForwardRecordingInput
    ├── fixed state + slot-local shadow sampling handles
    └── all geometry + model/material values
```

The frame input and its pass views are non-copyable and non-movable. Their
constructors restrict provenance: the compiler creates the complete frame
input, which creates its pass views. The compiler owns reusable packet vectors
and forms the spans after both vectors have finished growing.

These are lifetime constraints as well as types. No CPU consumer may remain
when the compiler builds another input. Every helper is joined before the
recording call returns, including during exception unwinding. Command buffers
consume the packet values during recording; the separately owned GPU buffers,
images and samplers must survive until submitted work finishes.

## Ownership follows retirement and replacement

The important owners appear below in their relative declaration order in
`Renderer::Impl`; scalar configuration, counters and cached metadata are
omitted. [FrameResources][source-frames] groups the resources selected by a
submission-slot index.

```text
Renderer::Impl
├── Device
├── MemoryAllocator
├── ResourceCompiler
├── optional readback buffer
├── shadow-map creation tracker
├── shadow comparison sampler + ShadowPipeline
├── PresentationState
│   ├── Swapchain + render-finished semaphore per image
│   ├── forward DepthBuffer[2]
│   ├── ForwardPipeline
│   └── presentation fences + submitted flags per image
├── FrameResources[2]
│   ├── FrameSlot: image-available semaphore + fence + pending flag
│   ├── FrameUniformBuffer
│   ├── ShadowFrameResources: map + primary recording context
│   └── ForwardFrameResources: primary + two participant contexts
├── RenderPreparation + CompiledResources
├── FrameRecordingInputCompiler
├── ShadowRecorder
└── ForwardRecorder + persistent helper
```

Reverse destruction stops the helper before its borrowed contexts and resource
owners disappear. Destruction of submitted GPU resources also requires the
renderer to retire outstanding work; declaration order alone cannot do that.

| State | Index or lifetime | Replaced during presentation recreation? |
| --- | --- | --- |
| Shadow map and recording contexts | frame slot | no |
| Frame uniforms and submission synchronization | frame slot | no |
| Shadow pipeline and comparison sampler | renderer | no |
| Compiled scene resources and upload context | preparation / renderer | no |
| Forward depth attachments | frame slot, with presentation extent | yes |
| Forward pipeline | presentation attachment compatibility | yes |
| Swapchain images, views and render-finished semaphores | acquired image | yes |
| Presentation fences and submitted flags | acquired image | yes |

The [presentation owner][source-presentation] contains forward depth buffers
even though they are indexed by frame slot: their size changes with the
window. Fixed-resolution shadow maps belong to the frame resources and remain
independent of that replacement.

Two outstanding Vulkan submissions, one CPU frame being prepared, and one or
two forward recording participants are independent counts. The driver-selected
swapchain image count determines none of them.

## The frame and image-dependency protocol

The ordinary [draw call][source-renderer] follows this order:

1. Select the next frame slot and compile both pass inputs and matrices before
   acquisition. Invalid draw references or view values fail here.
2. Wait for that slot's submission fence, then write its shared uniforms.
3. Acquire a swapchain image using the slot's image-available semaphore.
4. Retire and reset the acquired image's earlier presentation fence if needed.
5. Reset and record the complete shadow primary, including depth publication.
6. Reset and begin the forward primary, record and join its participants,
   execute their secondaries, and finish the output transition.
7. Reset the slot fence immediately before submitting the shadow and forward
   primaries together. Mark work pending and advance the slot index only after
   submission succeeds.
8. Present using the acquired image's render-finished semaphore and presentation
   fence, then return the presentation outcome.

The [shadow recorder][source-shadow] owns both transitions in its image protocol:

```text
slot fence retires all previous uses of this map
                        |
                        v
discard old contents -> depth attachment -> render caster depths
                                                |
                                                v
                         depth-write to sampled-read barrier
                                                |
                                                v
                         forward fragment shader samples map
```

The entry transition uses an empty source scope and discards the old contents.
That is justified by the slot fence covering all prior uses, including sampled
reads. The exit barrier orders early/late depth-attachment writes before
fragment-shader sampled reads and changes the layout to read-only depth.

Both primaries are submitted to the graphics queue in shadow-then-forward
order. No semaphore connects the two passes. The swapchain acquisition wait
applies at colour-attachment output, while the map's own dependency is carried
by its barrier. One slot fence covers the complete submission.

Transition ownership follows the destination use. Each recorder establishes
its attachment layouts; the shadow recorder also establishes its fixed sampled
consumer layout. The coordinator chooses the final forward output transition
because presentation and capture have different output requirements.

## Forward recording remains a bounded parallel operation

[ForwardRecorder][source-forward] selects one participant below 10,000 forward
draws and two from 10,000 upward: at least 5,000 draws per participant. A forced
count is a diagnostic override; insufficient draws fall back to one. The
shadow pass records directly into its own primary and does not use this policy.

For two participants, the coordinator takes the first contiguous half, rounded
up, and the persistent helper takes the remainder. Each resets its own command
pool and establishes complete state in its secondary command buffer. The
primary executes the completed secondaries in original draw order.

The fixed state includes the selected slot's shadow image view and comparison
sampler. It is established in every actual forward draw command buffer, not
only in the primary. Each participant also starts with its own geometry and
base-colour-texture binding cache, so neither relies on another participant's
state.

The helper receives one copied job with borrowed packet/context storage. It
publishes completion even after an exception. The coordinator polls completion
for at most 50 microseconds before blocking; a scope guard joins outstanding
work if coordinator recording fails. Helper errors are rethrown on the
coordinating thread after completion has been observed.

`--forward-direct-primary` records forward draws directly into the primary as
a diagnostic comparison. It retains the empty secondary-pool reset used by
the measurement model. It changes neither the shadow pass nor the ordinary
automatic participant policy.

The [application options][source-options] make this forward-only scope explicit.
For commands carried over from 0.9:

| 0.9 option | 0.10 replacement |
| --- | --- |
| `--direct-primary` | `--forward-direct-primary` |
| `--recording-threads` | `--forward-recording-participants` |

Both old option names are rejected, not accepted as aliases. The participant
override takes `1` or `2` and includes the coordinator; it does not choose a
number of helpers or enable parallel recording of the shadow pass.

## Camera, shadow and shader contracts

Matrices are column-major, with right-handed views and zero-to-one projected
depth. Both passes use negative-height viewports, placing framebuffer Y
inversion in rasterization. The [forward shader][source-shader] maps projected
light coordinates to texture coordinates as `(0.5*x + 0.5, 0.5 - 0.5*y)`.

The shared [FrameUniforms][source-uniforms] stores camera and light
view-projection matrices in one 128-byte, 16-byte-aligned value matching Slang's
`Std140DataLayout`. Each slot owns one buffer updated after its fence retires.
Forward push constants hold the model matrix and base-colour factor; shadow
push constants contain only the model matrix.

The depth-only [shadow shader][source-shadow-shader] has a vertex stage and
position input, with no colour attachment or material sampling. Both pipelines
use the same vertex stride. The forward shader retains base-colour texturing
and passes light-clip coordinates through perspective-correct interpolation.

The fixed shadow configuration is deliberately small:

| Choice | Released behaviour |
| --- | --- |
| Map | one 1024-by-1024 depth image per frame slot |
| Format | prefer D32Sfloat, then D16Unorm, requiring sampled-image and depth-attachment support |
| Nominal texel storage | 8 MiB for two D32 maps, or 4 MiB for two D16 maps; allocation overhead excluded |
| [Comparison sampler][source-sampler] | nearest filtering, less-or-equal, opaque-white clamp-to-border |
| Raster bias | constant 1.25, clamp 0, slope factor 1.75 |
| Receiver offset | subtract 0.0015 from projected comparison depth |
| Demonstration light | eye (-4, 6, 4), target (0, -0.5, 0), Y up |
| Orthographic bounds | X/Y from -4 to +4, near 0.1, far 20 |

[Format selection][source-policy] is independent of the forward depth format:
an attachment-compatible format is not automatically suitable for sampling.
The shader treats non-positive clip W and depth outside zero to one as lit;
the white border handles coordinates outside the map in X/Y.

Visibility scales base-colour RGB between 0.35 and 1.0 while preserving alpha.
This is a shadow-visibility demonstration without normals or a diffuse/specular
lighting model. Hard edges and brief grazing-angle self-shadow breakup remain
accepted limitations. D32 was used in the reviewed device runs; D16 fallback
selection has device-free coverage, not an equivalent device-quality claim.
The [image notes][source-images] record the accepted configuration and limits.

## Replacement, exceptions and presentation outcomes

Resource preparation and presentation replacement install complete candidates.
If construction fails, the candidate is not installed. Stable resource
preparation retires outstanding work before old GPU resources can be released.
Presentation replacement also waits for the presentation fences before
replacing the swapchain-compatible group.

`RenderResult` separates normal presentation outcomes from exceptions:
presented, presented but suboptimal, or not presented because the swapchain is
out of date. An out-of-date acquisition submits nothing and leaves the slot
index unchanged. An out-of-date presentation occurs after submission, so its
slot has already advanced and its presentation-fence submission is recorded.

Invalid arguments, invalid engine state and runtime/device failures remain
distinct exception categories. A pre-acquisition validation failure leaves
no acquired-image semaphore to account for. A recording failure after
acquisition joins the helper and unwinds without submitting partial commands,
but the API does not promise that the caller can catch it and resume drawing
with another acquisition. Terminal cleanup and retry are different contracts.

Zero framebuffer extent makes `recreatePresentation()` return false. The
application waits for events and retries until drawable or closed. This path
does not imply that every minimised window reports zero extent: the reviewed
macOS window retained a nonzero extent and continued rendering while hidden.

## Capture and measurement are separate diagnostic paths

One-shot PNG capture is tied to a finite run and a presented-frame ordinal.
It preserves the capability to read back swapchain images across recreation.
On the capture attempt, the renderer records the copy and waits for the full
submission on the host before presenting; that presentation does not use the
ordinary render-finished semaphore wait. Conversion and encoding live in the
CPU capture utilities.

Capture therefore changes synchronization and cannot be combined with a
performance benchmark. Repeated captures can establish same-configuration
determinism; they are not evidence that the ordinary two-slot path overlaps,
nor are the committed macOS images portable pixel oracles.

Renderer timings are grouped into common, shadow and forward phases. The
benchmark combines the named host-work phases, excluding frame, acquisition
and presentation waits. It counts shared input/uniform work once, shadow reset
and recording once, and the coordinator-observed forward recording region
once. Overlapping participant diagnostics are not added to that total.

The sums do not enclose all application work or every pass-call bookkeeping
operation. They measure neither GPU time nor frame rate. Every synthetic
instance casts, so an N-instance benchmark has N shadow and N forward draws.
The [benchmark tooling][source-benchmark] records acquisition order, raw reports,
source/build/driver provenance, conditions and replayable analysis.

The released forward threshold remains 5,000 draws per participant. The
two-pass evidence supports a total-active-work improvement on laptop Lavapipe
at 10,000 draws while NVIDIA's corresponding result remains unresolved under
the registered drift rule. A forward-only improvement cannot resolve the
total-work question. This page records the retained policy, without claiming
a universal speedup or a newly located crossover.

## Build and test architecture

The [build][source-build] produces the engine library, an application-support
library for fixtures and benchmark helpers, the application executable, and
the Catch2 test executable. Slang compiles separate forward and shadow modules
with an explicitly tracked shared uniform declaration. Asset and shader paths
are absolute build-tree paths, so running from another working directory does
not change resource discovery. Header-selection checks guard against a
conflicting Vulkan SDK include path.

The Debug CTest suite contains **147 registrations**:

| Category | Registrations |
| --- | ---: |
| Device-free Catch2 cases | 94 |
| Device-free command-line rejection checks | 17 |
| Standard Vulkan device scenarios | 23 |
| Synchronization-validation device scenarios | 13 |
| Total | 147 |

The `device-free` label therefore selects 111 tests; `vulkan-device` selects
36. Counts come from configured registration, including CMake function
expansions and Catch2 discovery. Separately invoked Python suites test the
benchmark and validation-runner tools; they are not part of the 147.

Device scenarios use the real application, a shared CTest Vulkan resource
lock, 30-second timeouts and validation-error rejection. They cover automatic,
forced-participant and direct-primary paths, receiver reuse, preparation,
presentation recreation and capture. The 32-frame receiver reuse path avoids
capture and replacement waits. The eight-frame changed-caster scenario
prepares narrowed untextured replacement geometry after two original frames,
without a replacement image upload that could hide missing retirement.

[Linux CI][source-ci] runs the complete suite under Xvfb and Lavapipe. Its
[validation runner][source-validation] requires the pinned Khronos layer to
appear in both instance and device chains for each device test, including
wrapped captures. Synchronization runs enable shader descriptor-access
tracking. Missing-layer controls must be rejected by the runner, and restored
controls must show activation again. Debug validation remains optional for
ordinary application users; this stricter prerequisite belongs to CI.

Hosted macOS and Windows run all 111 device-free tests with
`--no-tests=error`; they do not claim device execution. Linux also runs the
Python tool tests and a separate observational Release benchmark. Formatting,
clang-tidy, dependency pins, terminology and the public/internal documentation
boundary have dedicated workflow checks. Public Doxygen excludes internal
detail headers and implementations; the internal site includes them.

## Seams and deliberate limits

**Pass order is fixed.** The coordinator knows shadow then forward. CPU pass
recording is serial, and the helper remains specific to forward secondaries.
There is no render graph, task queue or work-stealing scheduler.

**Preparation remains coarse.** Asset identity includes an address and revision.
A changed asset collection rebuilds the selected graph; there is no general
incremental reuse of unaffected meshes or textures. Uploads remain synchronous.

**Scene storage remains a forest with one component role per node.** Nodes are
individually allocated and append-only. The draw-list span and compiler arenas
still require callers to respect their reuse boundaries.

**Cast participation is attached to a render object.** Instances of the same
render-object ID share that policy. All forward objects receive shadows; there
is no independent receive toggle or general per-instance pass-policy system.

**The shadow model is deliberately limited.** It has one fixed orthographic
source and hard comparison sampling, with no cascades, dynamic fitting,
filtering, transparent casters, skinning or normal-based lighting. The fixed
frustum and bias are demonstration choices, not universal scene defaults.

**Validation and images establish different things.** A clean API run cannot
prove useful shadow content. Capture serializes its selected submission,
ordinary images cannot distinguish equal-valued uniform slots, and exercised
faults do not establish exhaustive race or lifetime correctness.

**Window recovery is not an idle-power policy.** Clean minimise/restore and
close behaviour does not establish zero rendering while hidden or exercise
every platform's zero-extent path.

**Measurement remains conditional.** The workload repeats opaque cube geometry,
and phase sums omit some bookkeeping. The threshold is an inherited policy
with stated uncertainty, rather than a prediction for arbitrary scenes or
Vulkan implementations.

## Where 0.11 can take this

The explicit pass boundary provides a place to investigate overlapping shadow
and forward CPU recording while keeping their GPU dependency ordered. Such a
change still needs to price dispatch, joining and contention against the work
it can overlap; this release supplies no measured pass-parallel speedup.

The other clear directions are normal-aware lighting and grazing-shadow
treatment, filtering, and scene/snapshot storage with better locality. They
address limits of the released model and need their own evidence. A more
general pass scheduler becomes justified when additional or dynamic passes
create requirements that this fixed sequence cannot express cleanly.
